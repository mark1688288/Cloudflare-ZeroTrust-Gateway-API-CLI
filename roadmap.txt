cloudflare-zero-trust-gateway-list-CLI
Roadmap
=======

Status: Phase 12 landed. Phase 9 and Phase 11 landed.
Rule: each later conversation implements exactly one step below, in order,
unless you explicitly skip or reorder.

Decided
-------
- Language: TypeScript (Node 22+ native type stripping; erasable syntax only)
- Default block source: OISD Small only
- OISD Small URL: https://small.oisd.nl/ — format is adblock, not hosts
  (OISD retired hosts/domains syntax on 2024-01-01; the bare URL is
  Adblock Plus, ||domain^)
- Default allow sources: personal file only (no silent public allowlists)
- CLI commands: compile / diff / apply / why
- Runtime config: config.yaml
- Hosting: this private repo; Actions checkout THIS repo, never upstream CGPS
- Auto-apply is OFF until Phase 7. Weekly job compiles only.
- Path model: the clone is the world. Resolve relative paths from repo
  root (parent of src/) with path.resolve. Pass absolute paths through.
  Never path.join(repoRoot, absolutePath).
- Snapshot contract (apply reads only this):
    snapshots/desired.json   compiled {domain, sourceId}[] + fold/budget
    snapshots/sources.json   ETag / SHA-256 / line count / fetch time
                             SHA-256 = decoded UTF-8 content identity
                             (Phase 3 records it; Phase 11 compares it)
                             ETag = HTTP cache validator only
                             (Phase 12; representation-dependent)
    snapshots/dropped.json   overflow, never silent truncate
    snapshots/account-quota.json  live other/owned list counts (Phase 10)
    snapshots/suggested.json      Gateway DNS blocked ranking (Phase 9)
  desired.json is version 2 / phase 3: compiled {domain, sourceId}[] plus
  folded metadata and remote.fetched[]. Phase 0 parse dumps are stale.
  diff / apply must reject an unknown or stale schema.
- Public suffixes (co.uk, com.hk, github.io) are never list entries and
  never fold parents. Private PSL entries count (tldts allowPrivateDomains).
- @@|| adblock exceptions in a block source are ignored, not turned into
  allow entries (no silent public allowlists).
- Actions apply consumes the compile job's artifact. Do not re-fetch
  remotes in the apply job.
- Exit codes: 0 ok, 1 usage/config, 2 refuse/safety/not-implemented, 3 API
- Own only lists/rules whose names start with "gateway-list"
- Other lists are never mutated or deleted. They still consume the
  account Gateway list quota (items + list slots). Phase 10 counts them.
- Source SHA-256 is the decoded UTF-8 content identity. A hash
  change is not a safety abort (OISD updates). Shrink stays on
  line count. ETag is not identity (Phase 12).
- Gateway DNS suggested allows are review-only
  (allowlist/suggested.txt). Never auto-merge into personal.
  Never commit suggested.txt / suggested.json (live DNS activity).

Phase 9 — Logs feedback (done)
------------------------------
Gateway DNS activity → a review-only suggested allow list.

Research (2026-08-15) — do not re-litigate unless the GraphQL schema
changed:

- Confirmed dataset. Official Gateway analytics docs (2026-04-24)
  list gatewayResolverQueriesAdaptiveGroups as "Gateway DNS queries
  with adaptive sampling". Sample query groups by
  queryNameReversed + resolverDecision and returns count.
    https://developers.cloudflare.com/cloudflare-one/insights/analytics/gateway/
- HTTP is a different dataset (gatewayL7RequestsAdaptiveGroups).
  This repo is DNS lists. Feasibility study said
  "Gateway DNS activity → allowlist/suggested.txt". DNS only.
- queryNameReversed is the DNS name with labels reversed
  (com.example.ads → ads.example.com). Strip a trailing dot.
  Then run normalizeDomain (PSL / punycode).
- resolverDecision is a uint8 in GraphQL, not a string. Live
  error if you pass names: `resolverDecision_in: not a number`.
  Official activity-log enum (2026-04-30):
    3 blockedByCategory
    4 allowedOnNoLocation
    5 allowedOnNoPolicyMatch
    6 blockedAlwaysCategory
    7 overrideForSafeSearch
    8 overrideApplied
    9 blockedRule
    10 allowedRule
  Filter with [3, 6, 9]. A 2026-08-15 probe on this account
  was 9600×5 + 9450×10 + 550×9 — treating the field as a
  string dropped every row and reported empty.
- Endpoint is POST https://api.cloudflare.com/client/v4/graphql
  — not under /accounts/{id}/. Token needs Account Analytics
  Read in addition to Zero Trust. Missing permission is expected
  (403 / unknown field); do not fail weekly compile.
- Adaptive counts are sampled. Use them to rank, not as an
  exact query total.
- 7-day window matches the weekly job. If the plan rejects the
  range, retry 1 day. If resolverDecision_in is rejected, retry
  without that filter and drop non-blocked rows client-side.
- desired.json cannot be the review surface. Suggestions are

- Do not open a GitHub PR. compile job is contents:read. Review

Phase 10 — Account quota includes other lists (done)
----------------------------------------------------
The Job Summary line `used: 56846 / 300000` is compiled allow+block
only. It is not the Cloudflare Zero Trust account Gateway-list quota.

Research (2026-08-15) — do not re-litigate unless the API changed:

- Confirmed gap. `summary.ts` does `used = allow.length + block.length`
  against `plan.max_items`. Compiler `applyBudget` uses the same number.
  Neither path reads Cloudflare.
- `lists` already fetches every Gateway list and then prints
  `other lists: N (ignored)`. in-practice: 58 owned + 88 human lists
  after the first apply. Those 88 are dashboard/API-created (any type).
- Phase 5/6 correctly ignore other lists for *management* (never
  PATCH/delete them). That stays. The bug is *not counting* them.
- Cloudflare has no quota endpoint. Item count is per-list
  `count` ("Indicate the number of items in the list") on the
  GatewayList object:
    GET /accounts/{id}/gateway/lists              inventory
    GET /accounts/{id}/gateway/lists/{list_id}    one list
      https://developers.cloudflare.com/api/resources/zero_trust/subresources/gateway/subresources/lists/methods/get
  Same schema on both: `{ id, count, name, type, items, … }`.
  `count` is optional. Client already has `listLists` + `getList`.
  Account item usage = sum of `count` across *all* lists, not just
  `gateway-list*`. Prefer the list-all `count` (one paginated GET).
  If a row omits `count`, GET that `{list_id}` for the number — do
  not paginate `/items` just to count, and do not treat missing
  list-all `count` as 0. Apply still fail-closed if GET also has
  no count.
- The TypeScript docs page is the same HTTP contract, not a
  different API:
    https://developers.cloudflare.com/api/typescript/resources/zero_trust/subresources/gateway/subresources/lists/methods/get
  Official SDK shape: `client.zeroTrust.gateway.lists.get(listID,
  { account_id })` → `GatewayList` with every field optional,
  including `count?`. That confirms missing `count` is real in
  the published type, not just the HTTP example. Do not add the
  `cloudflare` npm package for Phase 10 — this repo already has
  `listLists` / `getList`, token-bucket, 429, and success:false
  handling. Runtime deps stay yaml + tldts.
- All list types share the pool: SERIAL, URL, DOMAIN, EMAIL, IP,
  CATEGORY, LOCATION, DEVICE, AAGUID. A human IP/email list still
  burns item + list slots. Count every non-prefix list, do not
  filter to DOMAIN.
- Two independent caps:
    items      plan.max_items (this repo: 300000). Official Standard
               is 1,000 entries/list; Enterprise 5,000 (already
               `items_per_list`).
    list slots official default (docs 2026-06-25) is 100 lists.
               Community / this repo historically assumed 300 lists ×
               1,000 = 300k. This account already has 146 lists, so
               100 is not the live cap here. Do not hardcode 100.
- Duplicates across a human list and an owned list both count.
  Do not subtract overlapping domains from other lists.
- Weekly compile job does not currently receive CLOUDFLARE_* env
  (only apply does). Display-only fixes in `lists` will not fix the
  Job Summary the operator actually reads.

Must have:

- Pure helper from the already-fetched list rows, e.g.
    owned_lists / other_lists
    owned_items / other_items   (sum of `count`; missing count =

    account_items = owned_items + other_items
    other: [{ name, type, count }]
  Persist `snapshots/account-quota.json` with fetchedAt + those
  totals (and the other-list table). Unknown counts stay explicit.

- `lists`: stop saying other lists are ignored. Print each other
  list (name, type, count), then
    items:  owned + other = account / max_items
    slots:  owned + other lists
  Write account-quota.json. Still read-only.

- `compile` stays usable offline (no token required). When

- `summary` Quota section (and therefore Actions Job Summary):
    allow / block / folded / dropped          (unchanged)
    compiled: <allow+block>
    other lists: <items> items / <n> lists    (or unknown)
    account: compiled + other / max_items     (projected if we

    list slots: owned_needed + other / max_lists if set

- `apply` and `--dry-run`: always live-read all lists (not the

Phase 11 — Compare SHA-256 to last successful source (done)
------------------------------------------------------------------
Phase 3 writes sha256 into snapshots/sources.json. Nothing reads it
back. The only vs-previous source gate is line-count shrink. A
byte-identical OISD refetch still re-downloads and looks like a
fresh source; a wholesale rewrite that keeps roughly the same
line count does not trip shrink.

Research (2026-08-15) — do not re-litigate unless OISD/Node fetch
headers changed:

- Confirmed gap. compile `okRecord` sets
    sha256: sha256Hex(text)
  of the decoded UTF-8 body. previousRecord() already loads last
  sources.json, but the only consumer is sourceShrank(lineCount).
  sha256Hex is tested for stability only. summary does not print
  the hash. etag is stored the same way and also never sent back.

- Two fields, two jobs. Do not collapse them.
    SHA-256  content identity of the *decoded* source text
             (path file bytes, or URL body after gunzip).
             Same list, two encodings → same hash.
    ETag     HTTP cache validator for *this representation*.
             OISD Vary: Accept-Encoding. Gzip and identity have
             different ETags for the same list. Phase 12.

- Live OISD Small probe (https://small.oisd.nl/, 2026-08-15):
    identity  Content-Length 1263371  ETag "6a7fbb38-13470b"
    gzip      Content-Length  477945  ETag "6a7fbb38-74af9"
    Node fetch (current CLI headers) stores the gzip ETag and
    decodes to 1263371 bytes. SHA-256 of that text is
      8129531e1ddfcebe76205b34048fd7b54fc828a84a974d8dbfecdb2119b9712f
    which already matches today's snapshots/sources.json for
    oisd-small. The identity is sitting there unused.
    cache-control: public, max-age=3600, must-revalidate
    last-modified is also sent. Weekly job is always past max-age.
    304 works (see Phase 12). This phase still always GET.

- desired.json cannot stand in for source text. It is post-fold
  and post-budget. Replaying last compiled domains for a source
  would drop folded children and already-dropped overflow. The
  compiler still needs the raw text. Phase 11 does not persist a
  body cache and does not skip compile.

- Hash change is not a safety abort. OISD Small updates often.
  abort_if_source_shrinks_pct stays on lineCount. Unchanged
  bytes cannot shrink (same text → same line count). Updated
  bytes still run today's empty + shrink gates.

- Do not skip writing desired.json just because every source
  hash matches. Live account-quota (Phase 10) can shrink the
  budget with identical sources. Local files, config, and
  compiler rules can also change independently of remotes.

- Do not send our SHA-256 as If-None-Match. Servers do not
  know it. Do not treat a missing previous sha256 as a mismatch
  abort; that is a first-seen / old-snapshot case ("new").

Must have:

- After a successful path read or URL 200, compute sha256Hex(text)
  and compare to previousRecord(...).sha256 when previous.status
  is "ok" and sha256 is a 64-char hex string.
    new        no usable previous hash (first compile, or last
               row was optional-failed / sha256 null)
    unchanged  hashes equal
    updated    hashes differ
  Persist that as SourceRecord.content. Keep sha256 / etag /
  lineCount as today. Do not bump desired.json version; this is
  not the apply contract. Old sources.json without `content`
  remains readable (treat as no previous identity).

- Remote and local sources both compare. oisd-small is the
  default URL case; personal / personal-block compare too.
  optional-failed rows stay sha256 null, content omitted.

- compile log names the outcome, e.g.
    source: oisd-small url https://small.oisd.nl/ unchanged (56949 lines, 56935 domains)
  summary Sources table gains a content column (new / unchanged
  / updated). Job Summary therefore shows whether OISD moved.

- Shrink / empty / required-404 behaviour unchanged. Unchanged
  sources still go through the compiler with the others.

- Tests (mock fetch, no live OISD required):
    second compile, same body → content=unchanged, same sha256
    second compile, different body under shrink threshold →
      content=updated, compile succeeds
    second compile, body shrunk past abort_if_source_shrinks_pct →
      exit 2, snapshots not overwritten
    first compile / missing sources.json → content=new
    local path file hash compare works without a URL

Done when (all verified):
- A second compile of today's oisd-small bytes records

- Changing the mock body without a 40% line drop records

Phase 12 — Conditional GET with ETag (done)
-------------------------------------------
Skip the URL body when the origin says 304. SHA-256 stays the
content identity (Phase 11). This phase is transport only.

Research (2026-08-15) — same OISD probe as Phase 11:

- OISD *does* 304 when If-None-Match equals the ETag of *this
  representation*:
    GET + identity ETag, no Accept-Encoding     → 304
    GET + gzip ETag + Accept-Encoding: gzip     → 304
    GET + identity ETag + Accept-Encoding: gzip → 200 (gzip body,
      different ETag)
    GET + gzip ETag, no Accept-Encoding         → 200 (identity)
    GET + both ETags in one If-None-Match       → 503
    HEAD + matching ETag                        → 304
  Do not send a list of ETags to OISD. Match one validator to
  the Accept-Encoding we will actually use.

- Today's CLI (Node fetch, no explicit Accept-Encoding) sends
  gzip, stores ETag "6a7fbb38-74af9", decodes to the identity
  bytes. Sending that gzip ETag back *without* gzip is a miss
  and re-downloads ~1.2 MiB. Pin the encoding (identity *or*
  gzip, pick one and keep it) so the stored ETag is reusable.

- 304 has no body. The compiler still needs raw text. Cannot
  rebuild it from desired.json (post-fold / post-budget). Must
  persist the last decoded body, e.g. snapshots/cache/<id>.txt,
  and on 304 reuse that file only if its sha256Hex still equals
  the previous record. Cache miss / hash mismatch → unconditional
  GET, then refresh the cache.

- Do not commit the OISD body to git unless you change the
  brief (≈1.2 MiB, noisy weekly diffs). Actions compile does not
  download the previous compile artifact today, so a gitignored
  cache only helps local re-runs. Restoring last week's artifact
  cache is a separate workflow change; not required to land the
  fetch/304 path itself.

- last-modified exists; prefer ETag. max-age=3600 does not
  replace revalidation on a weekly job.

- 304 is not a safety signal. After a cache hit, run Phase 11
  compare (should be unchanged) and the rest of compile as usual.
